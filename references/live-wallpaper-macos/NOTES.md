# LiveWallpaper (thusvill/LiveWallpaperMacOS) — Notes for Wallwright

Repo snapshot reviewed: `references/live-wallpaper-macos/repo` (branch `objectiveC`, GPL-3.0, "Paused Until End Of Aug 2026"). Files cited below are relative to that repo root.

## What it is

An open-source macOS 14+ live-wallpaper app: point it at a folder of `.mp4`/`.mov` files, pick one per display from a thumbnail grid, and it plays the video full-screen behind the desktop icons, with volume, scale-mode (fill/fit/stretch/center/height-fill), rotation, and a vignette-bar overlay option. Unlike Wallwright it does **not** hook the lock screen/aerials system (`README.md` explicitly: "currently LiveWallpaper doesn't support videos on the lock screen") and has no scene/web wallpaper support — it's video-only, same as Wallwright post-scope-cut. The codebase is mid-migration: a legacy hand-built AppKit UI lives in `LiveWallpaper.mm` (NSCollectionView grid, NSStackView settings panel, custom TouchBar) alongside a newer, cleaner SwiftUI front end (`ContentView.swift`, `LiveWallpaperApp.swift`) that talks to the same Objective-C++ `WallpaperEngine` singleton — both appear to still be reachable from the build, i.e. two UIs for one engine.

## Why Objective-C++ instead of Swift/AppKit

Worth noting since Wallwright is pure Swift. The `.mm` files aren't using ObjC++ for a graphics API Swift lacks — AVFoundation/CoreGraphics/IOKit are all equally reachable from Swift. What ObjC++ actually buys them here:

- **A C++ process-supervisor core wrapped in an ObjC shell.** `DisplayManager.h` defines `struct Display` and a bare `std::list<Display>` as global mutable state (not an NSObject/ObservableObject), manipulated with STL algorithms (`std::unordered_map`/`unordered_set` diffing in `ScanDisplays()`). That's a natural fit for C++, awkward to express as cleanly in Swift without wrapping the whole thing in classes.
- **`posix_spawn` + raw `pid_t`/`kill(2)`/`waitUntilExit` process management** (`WallpaperEngine.mm: launchDaemonOnScreen:`, `DisplayManager.h: KillProcessByPID`) — this is POSIX C, equally callable from Swift via `import Darwin`, but it reads as far more natural in a C++/ObjC++ file that's already importing `<spawn.h>`, `<signal.h>`, `<unistd.h>`.
- **Mach-level memory introspection**: `LogMemoryUsage()` in `LiveWallpaper.mm` calls `task_info(mach_task_self(), TASK_VM_INFO, ...)` directly — again possible from Swift but this is the kind of low-level system code where ObjC++/C idioms are the path of least resistance.
- **A private/undocumented display-info symbol loaded via `dlopen`/`dlsym`** (`DisplayManager.h: GetCoreDisplayInfoFn`) to pull `DisplayProductName` out of `CoreDisplay.framework` for human-readable monitor names — again equally doable from Swift, but this kind of "reach into a private framework function pointer" hacking is culturally more of a C/ObjC habit.

Net assessment: this isn't "ObjC++ can do things Swift can't" so much as "the author built a C++ state-management core (process table, YAML persistence, display diffing) and wrapped it in ObjC for AppKit/AVFoundation interop, then bolted SwiftUI on top later." The interesting architectural lesson for Wallwright isn't the language choice — it's the **separate-daemon-per-display process architecture** the C++ core exists to support (see Finding 1).

## Findings

### 1. One `wallpaperdaemon` subprocess per display, not one process with N windows — Performance, adopt-partial

`WallpaperEngine.mm: launchDaemonOnScreen:imagePath:displayID:` (and the duplicate `launchDaemon`/`launchDaemonOnScreen` free functions in `LiveWallpaper.mm`) `posix_spawn`s a *separate executable*, `Contents/MacOS/wallpaperdaemon` (source: `wallpaperdaemon/daemon.mm`), for every connected display, passing video path / static-frame path / volume / scale-mode / display-UUID as argv. Each daemon is its own `NSApplication` (`NSApplicationActivationPolicyAccessory`) with its own `AVQueuePlayer`, its own borderless desktop-level `NSWindow`, and its own run loop (`main()` at the bottom of `daemon.mm`). The main app tracks daemon PIDs in `Display.daemon` (`DisplayManager.h`) and cross-process-signals them via `CFNotificationCenterGetDarwinNotifyCenter()` Darwin notifications (`com.live.wallpaper.volumeChanged`, `.scaleModeChanged`, `.spaceChanged`, `.terminate`, `.autoPauseChanged` — registered in both `WallpaperEngine.mm` and consumed in `daemon.mm`'s `main()`). Killing a display's wallpaper is `kill(pid, SIGTERM)`/`killall wallpaperdaemon`, not window teardown.

- **Wallwright comparison**: Wallwright already handles multi-display via one `NSWindow` per display *within a single process*, which is architecturally simpler and avoids N× AVFoundation/Cocoa/CoreAnimation init cost and cross-process IPC plumbing. The daemon-per-display model buys crash isolation (a hung/crashed decoder on one display's video doesn't touch the others or the main app) and lets macOS's task scheduler/jetsam treat each display's playback independently — real advantages if you ever see per-display GPU/decode instability. But it's a heavier, more failure-prone design overall (subprocess bundling in `Contents/MacOS/`, PID bookkeeping, `killall` cleanup races) for a problem Wallwright's single-process multi-window approach already solves more simply.
- **Verdict**: not worth adopting wholesale. The one transferable piece is the **Darwin notification pattern for cross-process settings pushes** — cheap, no polling, no shared file — worth keeping in mind if Wallwright ever needs a second process (e.g., a slimmer helper for `AerialsInjector` instead of `killall`-ing `WallpaperAgent` directly).

### 2. `AVQueuePlayer` + `AVPlayerLooper` for gapless single-video looping — Performance, adopt-as-is

`wallpaperdaemon/daemon.mm: setupWallpaperWithVideo:` builds playback as `AVQueuePlayer queuePlayerWithItems:@[]` + `[AVPlayerLooper playerLooperWithPlayer:player templateItem:item]`, not a plain `AVPlayer` with a manual seek-to-zero-on-`AVPlayerItemDidPlayToEndTimeNotification` loop. `AVPlayerLooper` is Apple's purpose-built API for exactly this case and avoids the decode-restart stutter/black-frame that a manual seek loop can produce at the loop boundary.

- **Applicability**: if Wallwright's `VideoWallpaperViewModel` currently loops via item-end notification + manual seek, swapping to `AVQueuePlayer`/`AVPlayerLooper` for the primary video player is a low-risk, self-contained win — it doesn't conflict with the separate muted audio-only `AVPlayer` workaround Wallwright already has for the lock/unlock audio-drop bug (that second player can loop the same way independently). Worth checking Wallwright's current loop implementation and switching if it's still manual-seek-based.

### 3. Occlusion-aware performance throttling, not just battery/focus-based — Performance, adopt/adapt (highest priority)

This is the standout finding. `wallpaperdaemon/daemon.mm: isWallpaperHiddenOnTargetDisplay` calls `CGWindowListCopyWindowInfo(kCGWindowListOptionOnScreenOnly | kCGWindowListExcludeDesktopElements, kCGNullWindowID)`, walks every on-screen window, computes each window's intersection with the daemon's target display bounds, and flags the wallpaper "hidden" if a window's coverage crosses thresholds (`largeArea` >=80% of display area, or >=95% width & >=75% height, or >=60% area & >=90% height, and `alpha > 0.2`). `checkAndUpdatePlaybackState` (polled every 2s via a tolerant `NSTimer`, plus pushed on app-activate/space-change notifications) folds this together with battery state (`isRunningOnBatteryPower`, IOKit power-source polling) and Low Power Mode (`NSProcessInfo.isLowPowerModeEnabled`) into one `reducedPerformanceMode` flag. `applyPerformanceSettings` then:
- halves/downscales `AVPlayerItem.preferredMaximumResolution` (floor 640x360; 0.5x factor when occluded vs 0.75x for plain battery/low-power),
- caps `preferredPeakBitRate` to 6 Mbps,
- drops effective playback rate to 0.75x via `playImmediatelyAtRate:` when occluded (visually imperceptible when nothing is showing the wallpaper, but keeps audio/sync state sane for instant resume),
- sets `AVPlayerLayer.contentsScale` to 1.0 (vs. the real backing scale) when in reduced mode, avoiding wasted Retina-resolution compositing for pixels nobody sees.

- **Why this matters for Wallwright specifically**: Wallwright's `VideoWallpaperViewModel.applyBatteryMode()` throttles on battery only, and pause policy is keyed off "other-app-fullscreen" / "other-app-focused" — which misses the very common case of a large *non-fullscreen* maximized window (browser, IDE, Finder) sitting on top of most of the desktop without ever going fullscreen or stealing focus from a specific "allowed" app. The occlusion check here is orthogonal to focus/fullscreen state and catches that gap. It's also cheap: one `CGWindowListCopyWindowInfo` scan on a 2s tolerant timer, not per-frame.
- **Recommended adaptation, not verbatim copy**: don't necessarily *pause* on occlusion (that can cause an audible/visual pop on resume) — instead use it purely as a resolution/bitrate/rate throttle signal alongside existing battery throttling, the way this code does. This is a genuine finer-grained performance layer to add to Wallwright's existing `keepRunning/mute/pause/stop` policy matrix.

### 4. Layer-clock-correct pause/resume — Performance, interesting/low-priority

`resumeAllPlayers` in `daemon.mm` doesn't just call `player.play`/`pause` — it explicitly manipulates `AVPlayerLayer.speed`/`.timeOffset`/`.beginTime` around `CACurrentMediaTime()` to keep the Core Animation layer's presentation clock consistent with the player's actual resume point. Plain `player.pause()`/`.play()` alone can occasionally leave the layer's internal clock slightly offset, causing a visible micro-jump on resume. Cheap to add if Wallwright ever sees resume-jump artifacts around lock/unlock or the AerialsInjector's `WallpaperAgent` restart; not urgent otherwise.

### 5. Hybrid push+poll lock detection — Performance/robustness, adopt if not already doing this

`daemon.mm` registers for `NSDistributedNotificationCenter` `com.apple.screenIsLocked`/`com.apple.screenIsUnlocked` (instant, push-based, no polling cost) as the primary signal, but *also* falls back to polling `CFPreferencesCopyAppValue(CFSTR("ScreenLocked"), CFSTR("com.apple.loginwindow"))` inside the same 2s reconciliation timer (`isScreenLocked`) — treating the private notification as "probably reliable but don't bet everything on it." Given Wallwright already pokes around undocumented territory for `AerialsInjector`, this defensive dual-signal pattern (fast push notification + slow authoritative poll as a correctness backstop) is a reasonable template for any of Wallwright's own lock-state-dependent logic.

### 6. UUID-keyed display identity across reconfiguration — Performance/robustness, verify Wallwright already does this

`DisplayManager.h` (`DisplayUUIDFromID`/`DisplayIDFromUUID`, via `CGDisplayCreateUUIDFromDisplayID`) and `daemon.mm: handleDisplayReconfiguration` (registered via `CGDisplayRegisterReconfigurationCallback`) consistently key persisted/tracked display state by the stable per-display UUID, not the ephemeral `CGDirectDisplayID` (which can and does change across sleep/wake, dock/undock, or display reordering). `SaveSystem.mm` persists exactly `{uuid, screen, video, frame, daemon}` as YAML to `~/Library/Preferences/LiveWallpaper.yaml`, and `SaveSystem::Load()` re-resolves `screen` from `uuid` on load rather than trusting the saved ID. Worth a direct check against Wallwright's own multi-display persistence (and `AerialsInjector`, which writes into a manifest keyed by display) — if Wallwright is keying anything by raw `CGDirectDisplayID` instead of a UUID, that's a latent "wallpaper jumps to wrong monitor after sleep/dock change" bug this project already hit and fixed.

### 7. `compatibleGlass()` — a clean macOS-26-Liquid-Glass-with-fallback helper — UI/UX, adopt-as-is

`ContentView.swift` defines a small `View` extension that checks `#available(macOS 20.0, *)` (their compile flag for the Liquid Glass API) to use a native `NSVisualEffectView`-backed material, else falls back to `.ultraThinMaterial`. (The same pattern is mirrored in the legacy ObjC settings window as an `NSGlassEffectView`-vs-`NSVisualEffectView` `#if __has_include` compile-time fallback.) This is a tidy, reusable one-liner pattern for getting native Liquid Glass on new macOS while degrading gracefully on older systems Wallwright still supports — directly reusable in Wallwright's SwiftUI surfaces (ClockOverlay chrome, settings panels) with minimal adaptation.

### 8. Per-display multi-select dock with a "which displays does this video apply to" affordance — UI/UX, adopt

`ContentView.swift`'s `DisplayDockView`/`DisplayButton` renders a row of pill buttons (one per connected display, showing `getDisplayName()`/`getResolution()`), multi-selectable, animated with `matchedGeometryEffect` + spring animation + a yellow selection ring/glow. Selecting a thumbnail then applies that video only to the selected display(s) (`WallpaperViewModel.startWallpaper(video:displays:)`). This is a genuinely nice, low-complexity UI affordance for "assign different wallpapers to different monitors" that Wallwright's explorer/playlist UI could borrow directly — worth checking whether Wallwright's current UI exposes per-display assignment as cleanly (vs. a single global playlist across all displays, per the architecture summary, which suggests it currently doesn't).

### 9. Resolution-quality badge on thumbnails (4K/HD/SD) — UI/UX, cheap adopt

`WallpaperEngine.mm: badgeFromVideoTrack:` derives a "4K"/"HD"/"SD" badge from `AVAssetTrack.naturalSize` (adjusted by `preferredTransform`) and stamps it onto the cached thumbnail via `NSBezierPath`+`NSColor` drawing (also mirrored in SwiftUI as `QualityBadge`). Minor but real UX value on a multi-monitor setup: lets a user glance at the grid and know which source videos are high-res enough for a 4K/5K display without opening each file. Cheap to compute (already loading `AVAssetTrack` for thumbnail generation anyway) and cheap to render.

## Surprising / elegant / cautionary

- **Cautionary — silent opt-in to Login Items.** The newer Swift `AppDelegate` (`LiveWallpaperApp.swift`) does `if !isLoginItemEnabled() { setLoginItem(enabled: true) }` unconditionally on first launch — silently registering the app to launch at login with no prompt. The *older* ObjC `AppDelegate` (`LiveWallpaper.mm: addLoginItem:`) explicitly asks via an `NSAlert` ("Start LiveWallpaper at login? Yes/No") before doing the same thing. This looks like a UX regression introduced during the Swift rewrite — a good cautionary example for Wallwright to avoid: don't let a rewrite silently drop a consent step that the old code had.
- **Cautionary — a per-character `NSTimer`-driven "typewriter" log animation.** `LiveWallpaper.mm: appendLogMessage:` animates the HEVC-transcode progress log one character at a time via a repeating `NSTimer` (10ms tick) that appends one glyph per fire. Cute effect (matches the black/green "terminal" `NSTextView` styling of that panel) but a performance-naive way to do it — a scheduled timer per log line, ticking once per character, is unnecessary GCD/timer churn for a purely cosmetic effect. If Wallwright ever wants a similar retro-console feel, do it as a single `withAnimation`/attributed-string batch reveal, not per-character timers.
- **Elegant — dual UI on one engine.** The coexistence of a hand-rolled NSCollectionView/NSStackView AppKit UI (`LiveWallpaper.mm`) and a SwiftUI front end (`ContentView.swift`), both driving the same `WallpaperEngine` singleton and `WallpaperEngine.h` C-ish interface, is a reasonable incremental-migration strategy if Wallwright ever needs to do a UI rewrite of its own without a big-bang risk — keep the engine/view-model layer UI-framework-agnostic so old and new UI can point at the same backend during a transition.
- **Elegant, worth stealing outright**: the `Display{uuid, screen, video, frame, daemon}` struct + UUID-based reconciliation in `ScanDisplays()` (diffs current `NSScreen.screens` against tracked displays by UUID, killing daemons for displays that disappeared, spinning up entries for new ones) is a clean, small, well-tested pattern for "keep persistent per-display state correct across arbitrary display topology changes" — exactly the kind of thing that's easy to get subtly wrong (and this project shows visible scar tissue from having gotten it wrong before, e.g. the commented-out `waitForScreensReady` retry-loop and the `usleep()` calls scattered around display/daemon timing).

## If I only had time for 3 things

1. **Occlusion-aware performance throttling** (Finding 3) — extend Wallwright's existing battery-based `applyBatteryMode()` with a `CGWindowListCopyWindowInfo`-based "is this display mostly covered by another window" check, and use it to drop `preferredMaximumResolution`/`preferredPeakBitRate` (not necessarily pause) independent of the existing focus/fullscreen policy matrix. Highest performance value found in this repo, directly fills a gap in Wallwright's current throttling logic, cheap to implement (a periodic window-list scan, no new dependencies).
2. **Switch to `AVQueuePlayer` + `AVPlayerLooper`** for primary video looping (Finding 2) if not already used — small, self-contained, removes any loop-seam stutter, no architectural risk.
3. **Verify/adopt UUID-keyed display persistence** (Finding 6) across Wallwright's multi-display state and `AerialsInjector` manifest — if any part of Wallwright persists or matches displays by raw `CGDirectDisplayID` rather than a stable UUID (`CGDisplayCreateUUIDFromDisplayID`), this repo's `ScanDisplays()`/`SaveSystem` shows both the failure mode (wallpaper reassigned to wrong monitor after sleep/dock changes) and a small, proven fix.
